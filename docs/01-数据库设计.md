# 校园二手交易小程序 — 数据库设计

> 技术栈：微信云开发（云函数 + 云数据库 + 云存储）
> 所有集合均为云开发自带的文档型数据库（类 MongoDB）

---

## 0. 命名与通用约定

| 约定项 | 规则 |
|---|---|
| 集合名 | 小写复数，下划线分隔，如 `users`、`products` |
| 字段名 | 小驼峰，如 `createdAt`、`sellerId` |
| 时间字段 | 统一存 `Date` 类型（云开发自动转 ISO），不用时间戳数字 |
| 主键 | 云开发自带 `_id`，业务上不自建 id |
| 逻辑删除 | 用 `status` 字段标记，不做物理删除 |
| 分页 | 游标分页（基于 `createdAt`），不用 skip/limit 深分页 |

### 为什么不物理删除

学生项目最常见的事故是"误删商品导致订单页报错"。统一逻辑删除后，订单、消息里引用的商品仍在，详情页显示"该商品已下架"即可，不会白屏。

## 1. users — 用户表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 用户 ID |
| `_openid` | string | 自动 | 云开发自动写入，用户唯一标识 |
| `nickName` | string | 是 | 微信昵称 |
| `avatarUrl` | string | 是 | 微信头像 URL |
| `studentNo` | string | 否 | 学号，未认证时为空 |
| `schoolId` | string | 是 | 学校 ID，默认取注册时选择的学校 |
| `schoolName` | string | 是 | 学校名称冗余存储，避免列表页联表 |
| `verifyStatus` | string | 是 | 认证状态：`none` 未提交 / `pending` 审核中 / `passed` 通过 / `rejected` 驳回 |
| `verifyReason` | string | 否 | 驳回原因 |
| `creditScore` | number | 是 | 信用分，初始 100，被举报扣分 |
| `status` | string | 是 | `active` 正常 / `banned` 封禁 |
| `createdAt` | Date | 是 | 注册时间 |
| `updatedAt` | Date | 是 | 更新时间 |

### 索引

```
_openid      : 唯一索引（云开发自动创建，无需手动）
schoolId + verifyStatus : 复合索引（后台按学校统计认证数）
```

### 权限规则

```json
{
  "read": "doc._openid == auth.openid",
  "write": false
}
```

> **为什么 write 设 false**：用户资料只能通过云函数改，避免客户端直接篡改 `verifyStatus` 或 `creditScore`。这条是整个项目安全的地基。

## 2. products — 商品表

> **这张表同时存「二手闲置」和「校园跑腿」两类内容**，靠 `type` 字段区分。
> 老数据没有 `type` 字段，一律按闲置处理（所以闲置那侧查询要用 `_.neq('errand')`，
> 不能用 `_.eq('goods')`，否则改造前发布的商品会集体消失）。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 商品 ID |
| `_openid` | string | 自动 | 发布者 openid（云开发自动写入） |
| `type` | string | 否 | `goods` 闲置（默认，老数据无此字段） / `errand` 跑腿 |
| `sellerId` | string | 是 | 发布者 `_id`，用于跳转卖家主页 |
| `sellerName` | string | 是 | 卖家昵称冗余 |
| `sellerAvatar` | string | 是 | 卖家头像冗余 |
| `title` | string | 是 | 标题，1–30 字 |
| `desc` | string | 是 | 描述，上限 500 字 |
| `price` | number | 是 | 价格，单位：元，保留 2 位小数（跑腿时为**酬劳**） |
| `oriPrice` | number | 否 | 原价，用于显示划线价（跑腿恒为 0） |
| `images` | array\<string\> | 是 | 图片 fileID 数组，最多 9 张（**跑腿可为空数组**） |
| `cover` | string | 是 | 封面图 = `images[0]`（跑腿无图时为空串，卡片走占位样式） |
| `categoryId` | string | 是 | 分类 ID（跑腿固定为 `'errand'`） |
| `categoryName` | string | 是 | 分类名冗余（跑腿固定为 `'校园跑腿'`） |
| `tradePlace` | string | 是 | 面交地点，**用户自由填写**（≤30 字；跑腿时存**送达地** `toPlace`，供列表卡片显示） |
| `schoolId` | string | 是 | 所属学校，同校过滤的核心字段 |
| `status` | string | 是 | `on_sale` 在售 / `sold` 已售 / `off_shelf` 主动下架 / `deleted` 已删除 / `blocked` 违规下架 |
| `viewCount` | number | 是 | 浏览量 |
| `favCount` | number | 是 | 收藏数 |
| `auditResult` | string | 是 | 内容安全检测：`pass` / `risky` / `pending` |
| `createdAt` | Date | 是 | 发布时间 |
| `updatedAt` | Date | 是 | 更新时间 |

### 跑腿专属字段（仅 `type === 'errand'` 时存在）

| 字段 | 类型 | 说明 |
|---|---|---|
| `errandType` | string | `express` 代取快递 / `buy` 代买 / `deliver` 代送 / `queue` 代排队 / `other` |
| `errandTypeName` | string | 类型名冗余，如「代取快递」 |
| `fromPlace` | string | 取件 / 购买地点 |
| `toPlace` | string | 送达地点 |
| `deadline` | Date | 期望完成时间（发布时校验必须晚于当前时间） |
| `errandStatus` | string | `open` 待接单 / `taken` 进行中 / `done` 已完成 / `canceled` 已取消 |
| `runnerId` | string | 接单人 `_id`，未接单为空串 |
| `runnerName` / `runnerAvatar` | string | 接单人信息冗余 |
| `runnerOpenid` | string | 接单人 openid（服务端用，不下发给客户端） |
| `takenAt` / `doneAt` | Date \| null | 接单时间 / 完成时间 |

**状态映射**：`open=on_sale`、`taken=trading`、`done=done`、`canceled=off_shelf`。
这样列表查询（只看 `status`）不用为跑腿单开一套。
**前端文案必须分开**：同一个 `on_sale`，闲置是「在售」、跑腿是「待接单」。

### 索引

```
schoolId + status + createdAt(降序)  : 核心索引，首页列表主查询
categoryId + schoolId + status + createdAt(降序) : 分类筛选
sellerId + status + createdAt(降序)  : 「我的发布」
title 全文索引（text）                : 搜索（云开发支持，需在控制台建）
```

> 首页查询是 `where(schoolId, status=on_sale).orderBy(createdAt desc)`，没有这个复合索引时数据量上千就会变慢。

### 权限规则

```json
{
  "read": true,
  "write": "doc._openid == auth.openid"
}
```

> `read: true` 让首页列表可以直接读数据库（减少云函数调用次数，省钱）。代价是别人能读到你的商品数据——这些本来就是公开信息，可接受。
> 写操作仍受限制，但**真正的写入口还是云函数**，因为要过内容安全检测。

## 3. orders — 订单表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 订单 ID |
| `orderNo` | string | 是 | 业务订单号，格式 `YYYYMMDD` + 6 位随机，用于展示 |
| `productId` | string | 是 | 商品 ID |
| `productSnapshot` | object | 是 | 商品快照：`{title, price, cover}` |
| `buyerId` | string | 是 | 买家 `_id` |
| `buyerOpenid` | string | 是 | 买家 openid，用于权限校验 |
| `sellerId` | string | 是 | 卖家 `_id` |
| `sellerOpenid` | string | 是 | 卖家 openid |
| `price` | number | 是 | 成交价（下单时锁定） |
| `status` | string | 是 | `pending` 待确认 / `trading` 交易中 / `done` 已完成 / `canceled` 已取消 |
| `cancelReason` | string | 否 | 取消原因 |
| `buyerRemark` | string | 否 | 买家留言 |
| `schoolId` | string | 是 | 学校 |
| `doneAt` | Date | 否 | 完成时间 |
| `createdAt` | Date | 是 | 下单时间 |
| `updatedAt` | Date | 是 | 更新时间 |

### 商品快照为什么必须存

卖家可能在下单后把商品删了或改价。如果不存快照，订单页要联查 `products`，一旦商品被逻辑删除就取不到标题和图片。**订单是财务级数据，必须自包含。**

### 状态流转

```
pending（买家下单）
  ├─ 卖家同意 → trading（约面交）
  │     └─ 卖家/买家确认 → done
  └─ 卖家拒绝 / 买家取消 → canceled
```

> 一个商品同时只能有一个非 `canceled` 的订单。下单时在云函数里先查一遍，防止被两个人同时下单。

### 索引

```
buyerOpenid + status + createdAt(降序)  : 「我的购买」
sellerOpenid + status + createdAt(降序) : 「我的卖出」
productId + status                      : 下单前置校验
orderNo                                 : 唯一索引
```

### 权限规则

```json
{
  "read": "doc.buyerOpenid == auth.openid || doc.sellerOpenid == auth.openid",
  "write": false
}
```

> 订单必须有服务端校验，`write` 设为 `false`。

## 4. messages — 消息表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | 消息 ID |
| `conversationId` | string | 是 | 会话 ID，规则见下 |
| `fromOpenid` | string | 是 | 发送者 openid |
| `fromId` | string | 是 | 发送者 `_id` |
| `toOpenid` | string | 是 | 接收者 openid |
| `toId` | string | 是 | 接收者 `_id` |
| `productId` | string | 是 | 关联商品，同一对人不同商品算不同会话 |
| `content` | string | 是 | 文本内容，上限 500 字 |
| `type` | string | 是 | `text` / `image`（预留） |
| `read` | boolean | 是 | 是否已读 |
| `auditResult` | string | 是 | 内容安全：`pass` / `risky` |
| `createdAt` | Date | 是 | 发送时间 |

### conversationId 生成规则

```js
// 两个 openid 排序后拼接 + 商品 ID，保证双方算出同一个 ID
const conversationId = [openidA, openidB].sort().join('_') + '_' + productId;
```

> 这样不需要额外的会话表，`messages` 里按 `conversationId` 分组就是会话列表。**排序是关键**，否则 A→B 和 B→A 会生成两个不同 ID。

### 索引

```
conversationId + createdAt(降序)  : 聊天记录分页
toOpenid + read + createdAt(降序) : 未读红点统计
```

### 权限规则

```json
{
  "read": "doc.fromOpenid == auth.openid || doc.toOpenid == auth.openid",
  "write": false
}
```

### 聊天方案：用 watch 而不是轮询

文档原方案说"先用轮询，别上 WebSocket"。这里改成**云开发数据库实时监听 `watch()`**：

| 方案 | 代码量 | 延迟 | 流量 | 云函数调用 |
|---|---|---|---|---|
| 轮询（3 秒） | 简单 | 0–3 秒 | 持续消耗 | 每 3 秒 1 次 |
| `watch()` | 差不多 | 准实时 | 按变更推送 | 0 次 |

`watch()` 是云开发原生能力，不需要自己维护 WebSocket 连接，掉线会自动重连。**在免费额度内完全跑得动**，而且用户体验好一个档次。

## 5. favorites — 收藏表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `_id` | string | 自动 | — |
| `_openid` | string | 自动 | 收藏者 openid |
| `userId` | string | 是 | 收藏者 `_id` |
| `productId` | string | 是 | 商品 ID |
| `productSnapshot` | object | 是 | `{title, price, cover, status}` |
| `createdAt` | Date | 是 | 收藏时间 |

### 索引

```
_openid + productId : 唯一复合索引（防重复收藏）
_openid + createdAt(降序) : 收藏列表
```

> 唯一索引是硬保障。客户端"先查再插"有并发窗口，双击收藏按钮就能插两条，唯一索引能直接挡住。

### 权限规则

```json
{
  "read": "doc._openid == auth.openid",
  "write": "doc._openid == auth.openid"
}
```

> 收藏是纯个人数据，可以让客户端直连写，取消收藏不用走云函数，响应更快。

## 7. 集合权限规则汇总

在云开发控制台 → 数据库 → 每个集合 → 权限设置 → 自定义安全规则，粘贴对应 JSON。

| 集合 | read | write |
|---|---|---|
| `users` | 仅自己 | ✗ |
| `products` | 所有人 | 仅自己 |
| `orders` | 买卖双方 | ✗ |
| `messages` | 收发双方 | ✗ |
| `favorites` | 仅自己 | 仅自己 |
| `reports` | 仅自己 | ✗ |

> **原则**：能用客户端直读的（列表、收藏）就放开，省钱；涉及状态流转、金额、审核的（订单、消息、认证）一律走云函数。
