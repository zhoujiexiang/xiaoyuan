6 次提到 **10 次（≈8s）**，并在最终仍取不到实例时显式打印

> **排查口诀**：断言 detail 是 `null` / `undefined` 时，先怀疑「页面实例没取到」，

## 一、第六轮：新增「退出登录 / 头像私聊 / 校园跑腿」三大功能

本轮不是修 bug，是加功能；但加完照样跑全量回归，确认**没有把已经修好的东西碰坏**。

### 1. 退出登录（3 项）

| 断言 | 结果 |
|---|---|
| App 暴露 `logout` / `setLoggedOut` | PASS |
| **退出后不自动登录、重新登录后恢复** | PASS `{blocked:true, flag:true, restored:true}` |

第二个是**核心回归**。原来的 `ensureLogin()` 只要发现没登录就会静默调 `user/login` 注册回来，

配套改了 `product/list` / `product/detail`：**未注册不再直接报错**，退化为「不过滤学校」的公开浏览。
不改的话，退出登录后首页会一片空白——用户会以为小程序坏了。

> 顺带说清楚：小程序**做不到解绑微信账号**（openid 是微信下发的，退出再进还是同一个人）。
> 所以这个功能是「清本机登录态 + 不再自动登录」，不是「注销账号」。弹窗文案按这个口径写。

## 一·A、第五轮：修复「点卡片 → 商品不存在或已删除」的**第二个真因**

用户反馈（真机调试 + 控制台截图）：点进商品显示「商品不存在或已删除」，
控制台里是这样一行：

```
[detail] 商品不可用(40401) id= undefined
```

### 排查：数据完全正常，问题在**传参**

| 检查 | 结果 |
|---|---|
| 直接查库（`user/getProfile` + `product/myList`） | 用户名下 1 条商品「九成」，`status = on_sale`，15:17:11 发布 |
| `product/detail` 用这条 id 调用 | `code = 0`，**能正常打开** |
| 首页 `product/list` | 返回 1 条，与页面实例里的 `list` 完全一致 |
| 关键线索 | 日志里的 `id = undefined` —— 详情页**收到的 id 就是空的** |

### 真因：组件的自定义事件名与内置事件 `tap` **同名**

```wxml
<!-- components/product-card/index.wxml：内部用了原生 tap -->
<view class="pcard" bindtap="onTap">
```
```js
// components/product-card/index.js：自定义事件也叫 tap
this.triggerEvent('tap', { id: this.data.item._id });
```
```wxml
<!-- pages/index/index.wxml：两种事件被同一个绑定接住 -->
<product-card bind:tap="onCardTap" />
```

一次点击，父页面 `onCardTap` 被调用**两次**：

1. **自定义事件**：`e.detail = { id: '真实id' }` → 跳转到正确的详情页
2. **原生 tap 冒泡出组件边界**：`e.detail = {}` → `e.detail.id === undefined`
   → 拼出 `/pages/detail/detail?id=undefined` → 云端查不到 → `40401`

即**每点一次卡片会跳两次页面**，用户最终停在那个坏页面上，看到「商品不存在或已被删除」。
本例与社区里「自定义事件与内置事件同名导致父组件被触发两次」的记录完全一致
（组件内部 `triggerEvent` 一次 + 原生事件冒泡一次，后者 `detail` 为空）。

### 修了什么（6 处）

| # | 问题 | 修法 |
|---|---|---|
| 1 | 自定义事件与内置 `tap` 同名 → 双次触发 | 事件名 `tap` → **`cardtap`**，4 个页面的绑定同步改（`index` / `myProducts` / `favorites` / `search`） |
| 2 | 组件内部的 tap 会冒泡出组件边界 | 组件根节点 `bindtap` → **`catchtap`**，从源头阻断冒泡 |
| 3 | 页面侧完全没有兜底 | 4 个页面 `onCardTap` 加 `const id = e.detail && e.detail.id; if (!id) return;`（`myOrders` / `chat` 本来就有，只有卡片页漏了） |
| 4 | 详情页把 `?id=undefined` 当合法 id 去请求云端 | `onLoad` 拦截 空 / `'undefined'` / `'null'`，直接按「不存在」展示，**不发请求** |
| 5 | 排查日志有歧义 | `console.warn` 改用 `JSON.stringify` —— 字符串 `"undefined"` 和真正的 `undefined` 在控制台长得一模一样，加引号才分得清 |
| 6 | 全局错误上报被工具噪声淹没 | `reportError` 过滤 `wx://not-found`；`onError` / `onUnhandledRejection` 不再自己先打一遍日志（同一条错误以前会打两遍） |

### 本轮新增的回归断言（5 项）

```
PASS  卡片宿主节点可被自动化选中          — 找到 1 个 .pcard-cell
PASS  内置事件名 tap 不再触发卡片跳转      — 页面栈深度 1 → 1（期望不变）
PASS  点击卡片 → 详情页拿到的 id 正确      — route=pages/detail/detail productId="8b221eee..."
PASS  详情页拦截 ?id=undefined（不发请求）  — productId="" notFound=true
PASS  源码文件全部为合法 UTF-8（防混合编码乱码）— miniprogram/ 下全部正常
```

第 2 条正是本次 bug 的复现条件：往组件宿主节点派发一个**空的 `tap`**
（等价于当年冒泡上来的那第二次调用），页面必须**不动**。

### 为什么这个 bug 一直躲过自动化测试

自动化的 `Element.tap()` 是**按节点派发**的，而卡片内部的 `.pcard` 节点在自定义组件里，
`page.$$()` 取不到（`product-card` 与 `.pcard` 都返回 0）——**真实触摸无法模拟**。

处置：给组件宿主节点加了 `class="pcard-cell"`（无样式，纯为可测），
宿主可被选中后，用 `Element.trigger('事件名', detail)` 就能直接验证事件契约，
把「两条通路各触发一次」这种问题钉死在测试里。

### 顺手排查出另一处真问题：**源码文件混合编码损坏**

排 bug 时逐个文件核对编码，发现 `miniprogram/pages/index/index.wxml` **不是合法 UTF-8**，
但编译、运行、接口全都不报错。逐字节定位后有 5 行损坏，其中**两行是用户可见文案**：

| 行 | 现状 | 正确内容 |
|---|---|---|
| 3 | `<!-- 鎼滅储妗? -->` | `<!-- 搜索栏 -->` |
| 11 | `<!-- 椤堕儴鎻愮ず鏉? -->` | `<!-- 顶部提示条 -->` |
| 35 | `<!-- 鍟嗗搧鐎戝竷娴侊紙涓ゅ垪锛? -->` | `<!-- 商品瀑布流（两列） -->` |
| 67 | `加载中` + 残缺省略号 | `加载中…` |
| 68 | 残缺破折号 + `没有更多` + 残缺字 | `— 没有更多了 —` |

**损坏规律**：多字节字符的**末字节被替换成 `?`**（每个 `?` 正好占一个字节，所以文件大小不变），
只在「GBK 写盘 / UTF-8 写盘 / 保持原编码」三种方式混用时发生。
影响仅限于这几行的显示，逻辑与数据完全不受影响。

**处置**：
1. 第 67、68 行的文案**直接取同款页面（`favorites.wxml` / `myProducts.wxml`）里的字节**，
   保证与其他页面逐字一致；3 行注释按上下文恢复。
2. 修复前先做了**归因实验**：把 `favorites.wxml` 复制一份，用编辑工具改它的纯 ASCII 部分，
   再逐字节比对——多字节字符**完全未被动到**，证明编辑工具是安全的，
   这次损坏是**早期遗留**，不是本轮改动引入的（否则以后每改一次都会坏）。
3. **加了一条永久守卫断言**（静态检查、不依赖云端）：遍历 `miniprogram/` 下全部
   `.js/.wxml/.wxss/.json`，用 `new TextDecoder('utf-8', { fatal: true })` 解码，
   任何一个文件不是合法 UTF-8 就 FAIL。修复后 84 个文件全部通过。

> 这条守卫值得留着：这类损坏**不报错、不崩溃**，只会让界面出现乱码，
> 靠人工看界面才发现——而历史上本项目已经踩过两次编码问题。

| 首页 `product/list` | 只返回「久」（在售），符合预期 |
| 收藏 / 订单 | 均为 0 条，不存在死卡片 |
| **真实 UI 复现**：发布页真实点击「发布」→ 自动回首页 → 点卡片 | 新商品**出现在首页列表**，详情页 `status=on_sale`、`notFound=false` —— **修复后的链路是通的** |

### 真因：用户的商品被**上一版测试脚本**下架了

`product/detail` 返回的是原始文档，里面有 `updatedAt`：

```
「九」 创建 createdAt = 2026-09-17 14:21:34
      最后更新 updatedAt = 2026-09-17 14:22:22   ← 发布 48 秒后
```

正是**第三轮第 6 条**记录的那个失败模式：旧版脚本用 `myList(status:'on_sale')[0]`
把**用户自己的第一个在售商品**当实验对象，对它点「下架」再「重新上架」；
第二步没成功 → 用户的商品被永久留在下架状态。
用户随后点进去看到的就是「已下架」（`status !== 'on_sale'` 时详情页顶部有状态条）。

**处置**：已通过 `product/offShelf {op:'on'}` 把「九」恢复为在售
（现在「久」「九」均为 `on_sale`）。这是回滚测试工具造成的副作用，可逆——
用户想让它下架的话再点一次即可。

### 本轮修的问题

| # | 问题 | 修法 |
|---|---|---|
| 1 | **刷新标记会被「吃掉」** | `index.js#onShow` 原来一进来就 `consumeListRefresh()`，而 `loadList` 开头有 `if (this.data.loading) return`——若此刻有请求在飞，标记被消费、刷新却没发生，列表仍是旧的。改为 `app.js#hasListRefresh()` 先 peek，**确认要发起刷新时才消费**；加载中则暂存，加载结束补刷 |
| 2 | **收藏列表留着「已删除」死卡片** | `myFavorites` 原来对已删除商品回退成快照并标 `status:'deleted'`，卡片可点但点进去必 404，且列表里没有任何入口能删掉它 → 永久占位。改为**不再返回已删除/档案不存在的商品**（下架/已售仍返回，它们的详情页正常） |
| 3 | **详情页 404 文案不可操作** | 改为「该商品已被删除，返回列表会自动刷新」+ 按钮「返回并刷新列表」，并把商品 id 打进 `console.warn`，真机排查有据可依 |
| 4 | **下架确认弹窗按钮是「确定」** | 详情页的上下架弹窗补 `confirmText`「下架」/「重新上架」+ 颜色区分，减少误点（下架会隐藏商品） |
| 5 | **DOM 断言偶发假失败** | 「我的」页面校名断言读得太早会读到 `userInfo:null` 的初始帧（「未选择学校」）。改为**轮询等待**直到出现校名 |

### 本轮新增的回归断言（3 项）

```
PASS  已下架商品详情页可正常打开(不报不存在)  — code=0 status=off_shelf
PASS  收藏列表不含已删除商品                — 收藏 0 条，其中已删除 0 条
PASS  用户真实商品状态未被测试改动            — 2 条真实商品状态不变
```

最后一条是**针对本次事故的硬防线**：脚本开跑前对用户真实商品做
「状态基线快照」，收尾时逐条比对，一旦被改动立刻 FAIL——
把「用户自己发现商品被下架」变成「测试当场报错」。

## 一、第三轮：修复「发布成功后点进商品提示不存在或已删除」

用户反馈：真机调试中发布商品成功，点进去提示**「商品不存在或已被删除」**。

### 排查过程（都是拿真实数据验的，不是猜）

1. **直接查库**：连上模拟器读云端 `products`，全表只有 5 条——
   3 条是 `deleted` 的测试残留（`detail` 对它们确实返回 40401，**这是正确的**），
   2 条是用户刚发布的「九」「久」，`detail` 都能正常打开。
2. **排除环境错位**：真机调试的 openid（`oN_Yz3WT...`）与模拟器**完全一致**，
   客户端直读与云函数读到的也是同一批数据 → 不存在两个云环境的问题。
3. **定位到真因**：在模拟器里实测 tabBar 页面栈：

   ```
   B after switchTab(publish): ["pages/publish/publish"]
   C publish-side lookup of index page: {"stackLen":1,"indexFound":false}
   ```

   **`getCurrentPages()` 在 tabBar 页面里只返回当前这一个页面。**
   而 `publish.js` 靠 `pages.find(p => p.route === 'pages/index/index')` 找首页实例来标记刷新
   → 永远 `undefined` → **标记刷新是静默空操作** → 发布成功回到首页，列表还是旧的
   → 用户点到的是一张**已经失效的旧卡片**（其商品已被测试脚本软删除）→ 404。

### 修了什么

| # | 问题 | 修法 |
|---|---|---|
| 1 | **发布后首页不刷新**（根因） | `app.js` 新增 `markListRefresh()` / `consumeListRefresh()` 全局标记；`publish.js` 改用它；`index.js#onShow` 消费标记后重拉。不再依赖页面栈 |
| 2 | **详情页把任何失败都说成「商品不存在」** | `detail.wxml` 原来只有 `wx:else` 一个兜底分支。改为 `wx:elif="{{notFound}}"`（商品不存在）+ `wx:else`（加载失败，带**重试**按钮），`detail.js` 按错误码分流 |
| 3 | **云函数把所有异常都当 404** | `product/detail` 的 `catch` 原来无条件 `throw E.NOT_FOUND`；现在只有「文档不存在 / id 非法」才 404，其余如实上抛为 50000 |
| 4 | **「我的发布」完全不刷新** | 补 `onShow` 重拉（收藏页、订单页原本就有，只有它漏了） |
| 5 | **点开失效商品后列表仍不刷新** | 详情页判定 404 / 下架 / 删除时都 `markListRefresh()`，返回列表即刷掉失效卡片 |
| 6 | **测试脚本操作用户真实数据**（严重） | 原第 263 行 `myList(status:'on_sale')[0]` 取的是**用户自己的第一个在售商品**，然后对它点「下架/重新上架」——中途失败用户商品就被留在下架状态。改为**只用脚本自建的商品**（标题 `[自动化测试] 闲置教材`），并加防御：选中的若不是测试商品就跳过 |

> 第 6 条影响真实数据，是本轮最该修的一条。用户数据库里「九」当前是 `off_shelf`，
> **无法确认是用户自己点的下架还是上一版测试脚本留下的**，已在测试报告中标出，未擅自改动。

### 本轮新增的回归断言（4 项）

```
PASS  详情：不存在的商品返回 40401            — ❌ 40401 商品不存在或已被删除
PASS  详情页区分「商品不存在」与「加载失败」   — notFound=true loadError=""
PASS  列表刷新标记为一次性消费                — {"ok":true,"first":true,"second":false}
PASS  标记刷新后回到首页会重新拉取列表         — loadList 被调用 1 次
```

最后一条是这次的核心回归守卫：**修复前该计数恒为 0**（发布后首页永不刷新）。

### 收藏链路（补齐历史覆盖缺口）

排查「商品是不是没有收藏」时发现：收藏功能本身是完整的（`toggleFavorite` / `myFavorites`），
但 e2e 里**只有「收藏列表不含已删除商品」这一条断言，收藏动作本身从未被测过**。补上两条：

- `收藏：点一次后进入我的收藏` —— 断言 `isFavorited === true` 且 `myFavorites` 能查到它
- `收藏：再点一次取消，移出我的收藏` —— 断言回到 `false` 且列表里已无（**必须取消**，
  否则 `favorites` 集合会留一条指向测试商品的脏记录）

用自建测试商品（`createdProductId`）来验，绝不碰用户真实商品。

**入口澄清（易误解）**：收藏按钮**只在「买家 / 路人」视角的详情页底部栏**出现；
**卖家看自己的商品时没有收藏按钮**（底部是 举报 / 下架 / 删除），跑腿的发布者与接单人也一样。
因此自查时若打开的是自己发布的商品，会误以为「没有收藏功能」。入口另一处在「我的」→「我的收藏」。

### 顺带查出并修掉两个真问题

**① 「我的收藏」首次进入永远空白（严重）**
`pages/favorites/favorites.js` 只有 `onShow`，且写成 `if (this.loaded) this.loadList(true)`；
首次进入时 `this.loaded` 是 `undefined`，**永远不进 loadList** → 页面一直显示「还没有收藏任何商品」。
用户收藏了商品却看不到，很容易误判成「收藏功能没做」。
同款守卫 `myOrders` / `myProducts` 都有 —— 但它们各自有 `onLoad` 兜底首次加载，唯独这里漏了。
**修复**：补 `onLoad() { this.loadList(true); }`。

> 这个 bug 之所以长期没被发现：**接口级断言全绿**（`myFavorites` 明明返回了数据），
> 坏的是页面。所以补了一条**页面级断言**：`收藏：首屏进入「我的收藏」能渲染出已收藏的商品`
> —— 断言页面 `data.list` 长度 ≥ 1（轮询读取，避免异步假失败），修复前必挂。

**② 收藏后详情页的收藏数不更新（体验）**
`detail.js#toggleFavorite` 只 `setData({ isFavorited })`，没管 `product.favCount`。
云函数那边是异步 `_.inc`，前端不跟着改 → 用户点完收藏，页面仍显示「0 收藏」，像没生效
（截图 `21-detail-favorited.png` 里就是星标已变、数字还是 0）。
**修复**：按 `±1` 同步更新 `product.favCount`（下限 0）。

**全量结果：91 / 91 通过，运行时错误 0 条。** 截图核对：`20-detail-buyer.png`（买家视角底部「☆ 收藏 / 联系卖家 / 立即购买」）、
`21-detail-favorited.png`（「⭐ 已收藏」）、`22-favorites.png`（收藏列表渲染出卡片，修复前为空态）；
另外 `20-detail-owner.png` 是**卖家视角**，底部只有「⚠️ 举报 / 下架商品 / 删除」—— 没有收藏按钮。

### 又一处：「收藏显示 1，点进去却什么都没有」（用户反馈）

上一轮修完「收藏页首屏不加载」后，用户仍反馈**数字与内容对不上**。探针查到的实情：

```
[getProfile]  stats.favCount = 1        ← 「我的」页显示的收藏数
[myFavorites] 返回 0 条                 ← 点进去是空的
[db] favorites 集合 1 条：productId=d83520e2... | 商品 status=deleted
```

两个问题叠加：

**① 统计口径与列表口径不一致（设计缺陷）**
`user/getProfile#stats.favCount` 直接 `favorites.where({ userId }).count()` —— 数的是**记录条数**；
而 `product/myFavorites` 会**过滤掉商品已删除 / 档案已不存在的条目**。
两处口径不同 → 数字比列表多，用户看到「收藏 1」点进去是空的。
**修复**：新增 `countValidFavorites()`，分批 join `products` 排除 `status==='deleted'`
（云函数端 `_.in` 数组上限 100，必须分批）；`myFavorites` 遇到失效收藏时**顺手删掉**（自愈）。

**② 测试自身留下了一条脏记录（流程缺陷）**
上一轮临时脚本收尾后自报「复核：我的收藏残留测试数据 **0** 条」，但库里其实还留着一条 —— 
因为**复核用的是 `myFavorites` 接口**，而它会把「商品已删除」的条目过滤掉，**永远显示无残留**（假阴性）。
**修正**：复核一律**直接查集合**（`wx.cloud.database().collection('favorites').count()`），
并加断言 `收藏：库中记录数与列表条数一致（无失效残留）`。这条脏记录已清除。

**新增断言 2 条**（共 93 条）：
- `收藏：商品被删除后收藏数不虚高（与列表口径一致）` —— 主动造场景：
  自建商品 → 收藏（数字 +1）→ 软删商品 → 断言数字**回落到收藏前**且列表同步为空。
  末次输出：`收藏前 0 → 收藏后 1 → 商品删除后 0；列表 0 条`。
- `收藏：库中记录数与列表条数一致（无失效残留）` —— 直接查库，不经过任何过滤接口。

**全量结果：93 / 93 通过，运行时错误 0 条。** 云函数 `user` / `product` 已重新部署（`--remote-npm-install`）。
