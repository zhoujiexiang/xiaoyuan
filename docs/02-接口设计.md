# 校园二手交易小程序 — 接口设计

> 所有接口统一走**云函数**，调用方式 `wx.cloud.callFunction({ name, data })`
> 云函数内部用 `action` 字段分发到具体方法
>
> ⚠️ **`action` 是分发键，业务动作参数一律叫 `op`。** 详见 0.2 命名约定。

---

## 0. 统一响应格式

所有云函数**必须**返回这个结构，前端才能写统一的错误处理：

```js
// 成功
{ code: 0, msg: 'ok', data: { ... } }

// 失败
{ code: 40001, msg: '未登录', data: null }
```

### 前端调用封装

```js
// utils/request.js
async function call(name, action, payload = {}, options = {}) {
  // action 必须最后合并 —— 否则 payload 里的同名字段会顶掉分发键
  const res = await wx.cloud.callFunction({ name, data: { ...payload, action } });
  // ... 错误处理略
}
```

> 这段封装是后面所有页面的基础。**先写它，再写页面。**

### 0.2 字段命名约定（踩过坑，必读）

`action` 承担了**两个不能混淆的角色**：它是云函数 `switch (event.action)` 的分发键，
同时也出现在业务参数所在的同一个对象里。所以：

| 名字 | 用途 | 谁能用 |
|---|---|---|
| `action` | 分发到哪个方法，如 `'offShelf'` | **只能由 `call()` 的第二个参数填**，业务参数里禁止出现 |
| `op` | 业务动作，如 `'off'` / `'accept'` / `'block'` | 业务参数里统一的动作字段名 |

**为什么**：早期 `offShelf` 的入参写作 `{ productId, action: 'off' }`，
合并后 `event.action` 变成 `'off'`，云函数的 switch 匹配不到任何 case，
直接返回「未知的操作」。同理出现在订单状态流转、举报处理、商品强制下架、封禁用户上——
**五处功能静默失效，且不报错**。

两条防线（都已落地）：
1. `request.js` 里 `data: { ...payload, action }`，保证分发键永远最后生效；发现 payload 带 `action` 会 `console.warn`
2. `tools/check-api-contract.js` 静态核对前端字段与云函数读取字段，能直接报出死参数

## 1. 错误码表

| 区间 | 含义 |
|---|---|
| `0` | 成功 |
| `40000–40099` | 参数错误 |
| `40100–40199` | 未登录 / 登录失效 |
| `40200–40299` | 无权限（不是你的东西） |
| `40300–40399` | 业务规则不允许（如商品已售） |
| `40400–40499` | 资源不存在 |
| `40500–40599` | 内容安全拦截 |
| `50000+` | 服务端异常 |

### 具体错误码

| code | msg | 触发场景 |
|---|---|---|
| `40001` | 参数缺失 | 必填字段没传 |
| `40002` | 参数格式错误 | 价格不是数字、图片超 9 张 |
| `40003` | 内容过长 | 标题超 30 字、描述超 500 字 |
| `40101` | 未登录 | 取不到 openid |
| `40102` | 账号被封禁 | `status == banned` |
| `40103` | 未完成校园认证 | 需要认证才能发布 |
| `40201` | 无权操作 | 改别人的商品/订单 |
| `40301` | 商品已售出 | 下单时商品 `status != on_sale` |
| `40302` | 已有进行中的订单 | 同一商品重复下单 |
| `40303` | 订单状态不允许此操作 | 如已完成订单再取消 |
| `40304` | 不能购买自己的商品 | — |
| `40401` | 商品不存在 | ID 无效或已删除 |
| `40402` | 订单不存在 | — |
| `40501` | 内容含违规信息 | 内容安全接口返回 risky |

> **关于 `40401` 的边界（别踩）**：`product/detail` 只在**确实查不到该文档 / id 非法**时返回 40401。
> 权限、网络、数据库等异常会**如实上抛为 50000**，前端也按错误码分成两个分支展示——
> 404 显示「商品不存在或已被删除」，其余显示真实原因 + 重试按钮。
> 不要把两者合并：曾经 `catch` 无条件 `throw E.NOT_FOUND`，导致任何故障都伪装成
> 「商品不存在」，排查时全是误导。
>
> 前端的另一条约定：**列表页的「刷新」用全局标记，不用 `getCurrentPages()` 找页面实例**。
> tabBar 页面之间互相拿不到实例（`getCurrentPages()` 只返回当前这一个页面），
> 见 `app.js#markListRefresh()` / `consumeListRefresh()`。

## 2. 用户模块 `user`

### 2.1 `login` — 登录 / 注册

**入参**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `nickName` | string | 是 | 微信昵称 |
| `avatarUrl` | string | 是 | 微信头像 |
| `schoolId` | string | 否 | 学校 ID，首次登录时传 |

**返回**

```js
{
  isNewUser: true,          // 是否新注册
  userInfo: {
    _id, nickName, avatarUrl,
    verifyStatus, schoolId, schoolName, creditScore
  }
}
```

**逻辑**

```
取 openid → 查 users
  ├─ 存在 → 更新昵称头像（用户可能改了微信资料）→ 返回 isNewUser:false
  └─ 不存在 → 创建记录，verifyStatus=none，creditScore=100 → 返回 isNewUser:true
```

> **易错点**：`openid` 从 `cloud.getWXContext()` 取，**不能信任客户端传上来的**。这是安全底线。

### 2.2 `submitVerify` — 提交校园认证

**入参**：`{ studentNo, schoolId, schoolName, realName }`

**返回**：`{ verifyStatus: 'pending' }`

**逻辑**

```
校验学号格式（6–20 位数字字母）→ 查重（同一学号不能被两个账号绑定）
→ 更新 verifyStatus = 'pending'
```

> 学号查重很有必要。**否则一个学号能被无限个账号认证**，认证就失去意义了。

**入参**：无（从 openid 取）

**返回**：完整 `userInfo` + 统计数据

```js
{
  userInfo: {...},
  stats: { onSale: 3, sold: 5, favCount: 2 }
}
```

---

### 2.4 `auditVerify` — 审核认证（管理端）

**入参**：`{ targetUserId, pass: boolean, reason }`

**返回**：`{ ok: true }`

> 需要管理员权限。管理端可以先用云开发控制台手动改，**接口先预留**，后面做管理页面时直接用。

### 2.5 `getPublicProfile` — 看别人的主页

点头像进入对方主页时调用。

**入参**：`{ userId }`（对方的 `users._id`）

**返回**
```js
{
  userInfo: {
    _id, nickName, avatarUrl,
    verifyStatus, creditScore, schoolName, createdAt
  },
  isSelf: boolean,      // 是不是我自己
  banned: boolean,      // 对方是否已被封禁
  products: [...]       // 对方在售的二手闲置（最多 12 条，不含跑腿）
}
```

> ⚠️ **不返回 `studentNo` / `realName`**。
> 点头像就能看别人主页，把学号和真名带出去是隐私事故。
> `tools/e2e-test.cjs` 里有一条断言专门守着这条红线（断言名「用户主页不泄露学号/真名」），
> 改动这个接口时别手滑加字段。
>
> 允许未注册用户（游客 / 已退出登录）调用，方便匿名浏览。

## 3. 商品模块 `product`

### 3.1 `publish` — 发布商品

**入参**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `title` | string | 是 | 1–30 字 |
| `desc` | string | 是 | ≤500 字 |
| `price` | number | 是 | 0.01–99999 |
| `oriPrice` | number | 否 | 原价 |
| `images` | array | 是 | fileID 数组，1–9 张 |
| `categoryId` | string | 是 | 分类 |
| `tradePlace` | string | 是 | 面交地点，用户自由填写（≤30 字，云函数只校验非空） |
| `contact` | string | 否 | 联系方式 |

**返回**：`{ productId }`

**逻辑（顺序很重要）**

```
1. 校验登录 + 认证状态（未认证返回 40103）
2. 校验参数
3. 调 security.msgSecCheck 检测 title + desc  ← 先检测再入库
4. 违规 → 返回 40501，不写库
5. 通过 → 写 products，冗余卖家信息
```

> **为什么先检测再入库**：违规内容先入库再标记，会有一段"已发布"的窗口期。宁可让用户重新编辑。

> **图片检测在哪做**：图片是**客户端直传云存储**的（见 6.1），不经过 `product/publish`。
> 所以发布页的顺序是：
> `上传图片 → upload/imgSecCheck 检测 → 通过后调 product/publish`。
> 两步都在写库之前，任一环节不过就整单拦下并清掉刚上传的文件。

---

### 3.2 `list` — 商品列表

**入参**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | string | 否 | `goods` 闲置（默认，含无 type 的老数据）/ `errand` 跑腿 |
| `categoryId` | string | 否 | 分类筛选 |
| `keyword` | string | 否 | 搜索关键词（可与 `type` 组合：搜索跑腿任务时传 `type:'errand'`） |
| `sort` | string | 否 | `new` 最新（默认）/ `price_asc` / `price_desc` |
| `cursor` | Date | 否 | 分页游标 = 上一页最后一条的 `createdAt` |
| `pageSize` | number | 否 | 默认 10，上限 20 |

**返回**

```js
{
  list: [{
    _id, title, price, oriPrice, cover, tradePlace,
    categoryName, viewCount, sellerName, sellerAvatar, createdAt
  }],
  hasMore: true,
  nextCursor: '2026-09-16T12:00:00.000Z'
}
```

**逻辑**

```
默认只查本校（schoolId）且在售（on_sale）
关键字用正则模糊匹配 title
游标分页：where(createdAt < cursor).orderBy(createdAt desc).limit(pageSize + 1)
多取 1 条判断 hasMore，避免额外 count 查询
```

> **游标分页而不是 skip**：`skip(1000)` 在云开发里会真的扫过前 1000 条，越翻越慢。游标分页每页耗时恒定。
>
> **正则搜索的局限**：数据量上万后正则会很慢，需要换成云开发的全文检索或接入搜索服务。**实习项目阶段够用**，但要知道这是技术债。

---

### 3.3 `detail` — 商品详情

**入参**：`{ productId }`

**返回**

```js
{
  product: { ...完整字段 },
  seller: { _id, nickName, avatarUrl, creditScore, verifyStatus },
  isFavorited: false,
  isOwner: false
}
```

**逻辑**

```
查商品（不存在或 deleted → 40401）
attomic 更新 viewCount + 1
查卖家信息
查当前用户是否收藏
```

> **浏览量自增用 `_.inc(1)` 原子操作**，不要"读出来 +1 再写回去"，并发下会丢计数。

---

### 3.4 `offShelf` — 下架 / 重新上架

**入参**：`{ productId, op: 'off' | 'on' }`

**返回**：`{ status: 'off_shelf' | 'on_sale' }`

**逻辑**
1. 校验登录、sellerId == 当前用户，否则 40201
2. 被管理员强制下架（`blocked`）的商品，卖家不能自行上架 → **40309**
3. 有进行中订单（pending / trading）时不允许下架 → 40307
4. `op='off'` → `off_shelf`；`op='on'` → `on_sale`

---

### 3.5 `remove` — 删除商品

**入参**：`{ productId }`

**返回**：`{ ok: true }`

**逻辑**：校验归属 → `status = 'deleted'`（逻辑删除）→ 有进行中订单则拒绝。

## 3A. 校园跑腿（同在 `product` 云函数）

跑腿与闲置**共用 `products` 集合**，靠 `type` 字段区分。老数据没有 `type` 字段，按闲置处理。

**为什么共用**：列表、详情、搜索、收藏、举报、聊天都能直接复用，不用维护两套；
代价是列表查询必须显式排除另一类（漏了就会两类内容互相串，已有测试断言守着）。

### 3A.1 发布跑腿 —— 走同一个 `publish`，带 `type: 'errand'`

**入参**
```js
{
  type: 'errand',
  title, desc, price,          // price 即「酬劳」
  images: [],                  // 跑腿可以不配图（闲置必须至少 1 张）
  errandType,                  // express|buy|deliver|queue|other（白名单，与 config.js 一致）
  errandTypeName,              // 如「代取快递」
  fromPlace, toPlace,          // 取件地 / 送达地
  deadline,                    // 时间戳，必须晚于当前时间
  contact
}
```

**返回**：`{ productId, type: 'errand' }`

落库时额外写入：`errandType / errandTypeName / fromPlace / toPlace / deadline /
errandStatus='open' / runnerId='' / takenAt=null`；`categoryId` 固定为 `'errand'`，
`tradePlace` 取 `toPlace`（列表卡片上的 📍 显示送达地）。

### 3A.2 列表 / 详情

- `list` 增加可选入参 `type`：`'errand'` 查跑腿；不传或其它的按闲置处理
  （内部用 `_.neq('errand')`，**不能**用 `eq('goods')`，否则老数据会集体消失）。
- `detail` 返回的 `product` 里会带上全部跑腿字段，另外可以根据
  `product.errandStatus` 与接单人信息（`runnerId/runnerName/runnerAvatar`）渲染。

### 3A.3 `errandAccept` — 接单

**入参**：`{ productId }`

**返回**：`{ status: 'trading', errandStatus: 'taken' }`

错误：`40310` 不能接自己发布的任务 / `40311` 已被别人接走 / `40005` 不是跑腿任务。

> **并发要点**：接单用的是**带条件的原子更新** ——
> `where({ _id, status:'on_sale', errandStatus:'open' }).update(...)`，
> `stats.updated === 0` 就说明被别人抢先了。
> 如果写成「先 `get` 判断再 `update`」，两个人同时点会**两个都成功**，后写的把先写的顶掉。

### 3A.4 `errandFinish` — 确认完成

**入参**：`{ productId }`　**返回**：`{ status: 'done', errandStatus: 'done' }`

只有**发布者**能确认（接单人不能自己说完成了就完成）；未接单时调用报 `40312`。

### 3A.5 `errandAbandon` — 接单人放弃

**入参**：`{ productId }`　**返回**：`{ status: 'on_sale', errandStatus: 'open' }`

任务回到「待接单」，别人可以再接。仅接单人本人可调用。

### 3A.6 `errandCancel` — 发布者取消任务

**入参**：`{ productId }`　**返回**：`{ status: 'off_shelf', errandStatus: 'canceled' }`

用 `off_shelf` 而不是 `deleted`：任务从列表消失，但详情页仍能打开（显示「已取消」），
发布者自己也能在「我的跑腿」里查到历史。已完成的任务不能取消。

### 3A.7 `errandMyList` — 我的跑腿

**入参**：`{ role: 'publisher' | 'runner' }`

**返回**：`{ list, hasMore: false }`（不分页，最多 50 条 —— 单校任务量本来就小）

**跑腿状态机**
```
open ──接单──> taken ──发布者确认──> done
  ^              │
  └──接单人放弃──┘
open/taken ──发布者取消──> canceled
```
与 `status` 的映射：`open=on_sale`、`taken=trading`、`done=done`、`canceled=off_shelf`。
这样列表查询（看 `status`）不用为跑腿单开一套。

> 前端文案要**分开**：同一个 `on_sale`，闲置叫「在售」，跑腿叫「待接单」。
> 前端映射表在 `miniprogram/utils/constants.js`（`ERRAND_STATUS_TEXT`）。

### 3A.8 `errandRemove` — 删除已结束的任务

**入参**：`{ productId }`　**返回**：`{ ok: true }`

软删除（`status = 'deleted'`，与商品的 `remove` 同一套语义：数据留在库里，只是不再出现在任何列表）。

**只允许删除「已结束」的任务**（`errandStatus` 为 `canceled` 或 `done`），否则返回 `40312`：

- `open` 的任务列表里还有人能接，删了等于凭空拿走；
- `taken` 的任务有人正在跑，删掉会让对方的「我接的」凭空消失。

**仅发布者可调用**（`sellerId` 校验，非本人 `40303`）。

> ⚠️ **不能复用商品的 `remove`**：那个只检查 `orders` 集合里有没有进行中的订单，
> 而跑腿**根本不建订单**（任务本身就是订单），复用的结果是连 `trading` 的进行中任务也会被放行。
>
> 「我接的」（runner）列表**不提供**删除入口：接单人无权删发布者的记录。
> 若以后要做「只从我的列表里移除」，需要单独加 per-user 隐藏标记，不能直接删文档。

## 4. 订单模块 `order`

### 4.1 `create` — 下单

**入参**：`{ productId, remark }`

**返回**：`{ orderId, orderNo }`

**逻辑**

```
1. 校验登录
2. 查商品（40401）
3. 不能买自己的 → 40304
4. 商品必须在售 → 40301
5. 查该商品是否已有进行中订单 → 40302
6. 写 orders，存商品快照，status = pending
7. 商品 status 保持不变（等卖家同意才改）
```

> **第 4、5 步的检查有并发窗口**：两个人同时下单可能都通过检查。彻底解决要加分布式锁或唯一索引。
> **折中方案**：给 `orders` 建 `productId + status` 索引，下单前查；即使漏进两条，卖家在同意时再查一次就能拦住。**实习项目可接受**，但要知道这里有并发风险。

---

### 4.2 `updateStatus` — 变更订单状态

**入参**：`{ orderId, op, reason }`

`op` 取值与权限：

| op | 谁能操作 | 前置状态 | 后置状态 | 副作用 |
|---|---|---|---|---|
| `accept` | 卖家 | pending | trading | 商品改 `sold`，其他人无法再下单 |
| `reject` | 卖家 | pending | canceled | — |
| `cancel` | 买卖双方 | pending / trading | canceled | 商品恢复 `on_sale` |
| `complete` | 买卖双方 | trading | done | 商品保持 `sold`，记录 `doneAt` |

**返回**：`{ status: 'trading' }`

**逻辑**

```
校验订单归属（按 op 判断是买家还是卖家）
校验状态流转合法性（40303）
更新订单 + 联动商品状态
```

> **状态机必须服务端校验**。前端传什么 op 都信，用户就能把 `done` 改回 `pending` 刷单。

## 5. 消息模块 `message`

### 5.1 `send` — 发送消息

**入参**：`{ toId, productId, content }`

> 不要传 `toOpenid`。对端 openid 由服务端从 `users` 表按 `toId` 查出，
> 否则客户端可以伪造 `toOpenid` 把消息发给任意第三人。

**返回**：`{ messageId, conversationId, createdAt }`

**逻辑**

```
1. 校验登录
2. 不能给自己发
3. msgSecCheck 内容检测 → 违规 40501
4. 计算 conversationId
5. 写 messages
```

---

### 5.2 `listMessages` — 聊天记录

**入参**：`{ conversationId, cursor, pageSize }`

**返回**

```js
{
  list: [{ _id, fromOpenid, content, createdAt, read }],
  hasMore: false
}
```

**逻辑**：倒序查，前端反转显示。查完把对方发的消息标为已读。

---

### 5.3 `listConversations` — 会话列表

**入参**：无

**返回**

```js
{
  list: [{
    conversationId,
    peer: { _id, nickName, avatarUrl },
    product: { _id, title, cover },
    lastMessage: { content, createdAt },
    unreadCount: 2
  }]
}
```

**逻辑**

```
聚合 messages：
  match: 我是发送者或接收者
  group: conversationId
  last: 每个会话最后一条
  unread: 统计 toOpenid=我 且 read=false
按 last.createdAt 排序
```

> 这是云开发聚合（`aggregate`）的典型用法。**不要在前端循环调接口**，一次聚合搞定。

### 5.4 实时监听（不走云函数）

聊天页用云开发原生 `watch()`：

```js
const db = wx.cloud.database();
const watcher = db.collection('messages')
  .where({ conversationId })
  .orderBy('createdAt', 'asc')
  .watch({
    onChange: snapshot => {
      // snapshot.docs 是最新全量数据
      this.setData({ messages: snapshot.docs });
    },
    onError: err => console.error(err)
  });

// 页面 onUnload 时务必关闭
onUnload() { this.watcher && this.watcher.close(); }
```

> **必须在 `onUnload` 里 `close()`**，否则页面退出后监听还在跑，反复进出聊天页会累积泄漏，最后白屏。

## 6. 上传模块 `upload`

### 6.1 客户端直传（推荐）

图片**不走云函数**，客户端直接传云存储：

```js
const res = await wx.cloud.uploadFile({
  cloudPath: `products/${openid}/${Date.now()}-${index}.jpg`,
  filePath: localPath
});
// res.fileID 直接存进商品记录
```

> **为什么不上云函数**：云函数上传要先把图片转成 base64 传给云函数，体积膨胀 33%，还有 10MB 限制。**客户端直传又快又省**。

### 6.2 `getTempUrl` — 批量换取临时链接

**入参**：`{ fileIDs: [...] }`

**返回**：`{ urls: { fileID: tempUrl } }`

> 云存储的 `cloud://` 地址在 `<image>` 里可以直接用，通常不需要换。需要下载或给 web 端用时才调这个。

### 6.3 `imgSecCheck` — 图片内容安全

**入参**：`{ fileIDs: [...] }`（最多 9 张）

**返回**：

```js
{
  pass: true,          // 全部通过才为 true
  risky: [],           // 判定违规的 fileID 列表
  checked: 1,          // 实际送检张数
  total: 1,            // 传入张数
  results: { 'cloud://...': 'pass' | 'risky' }
}
```

**两个关键取舍**

1. **并行送检** —— 串行逐张累加耗时，9 张图很容易把云函数拖到超时。
2. **异常降级放行（fail-open）** —— 只有明确判定违规（`errCode 87014`）才拦。
   `security.imgSecCheck` 是同步接口，单图有 **1MB / 750x1334** 的尺寸上限，
   超限必然报错；若把「接口报错」也当违规，用户会莫名其妙发不出商品。
   代价是这类图会漏过，所以还有管理端人工下架兜底。

> 前端在 `publish.js` 的 `checkImages()` 里调用：判定违规就调 `deleteFiles` 清掉
> 刚上传的图片，再中断发布，避免违规内容进数据库、也避免云存储留垃圾。

### 6.4 `deleteFiles` — 删除文件

**入参**：`{ fileIDs: [...] }`

**权限**：只能删**自己**的文件 —— 校验路径里是否含自己的 `_id`
（路径形如 `products/{userId}/...`、`avatars/{userId}/...`）。

**返回**：`{ deleted: [...], failed: [...] }`

## 8. 接口设计原则（写代码前先记住）

1. **openid 永远从服务端取** — `cloud.getWXContext()`，客户端传的一律不信。
2. **状态流转只信服务端状态机** — 前端传 `op`，服务端判断能不能做。
3. **冗余换性能** — 卖家昵称、分类名、商品快照都存冗余，避免联表。
4. **先检测后入库** — 内容安全检测放在写库之前。
5. **列表用游标分页** — 不用 skip。
6. **涉及金额和状态的写操作一律走云函数** — 客户端只有读权限。
